# 阶段 4：开发执行

## 目标

按任务包修改代码，并在 `开发任务包/实施与静态检查记录.md` 中记录实施和静态检查；评审不通过后进入修复模式，每轮修复在同一份记录中追加 `## 轮次 E`（E 为实施轮次，见 Phase 5）。

项目相关的同步步骤、检查命令、专项约束都来自 SKILL.md「项目信息来源」；本文只规定流程。

## 1. 模式判定（命中即定）

| # | 条件 | 模式 |
| --- | --- | --- |
| 1 | 输入是 `评审报告.md` | 修复 |
| 2 | 实施记录已存在且含已完成轮次 | 修复 |
| 3 | 请求含修复意图（修复 / bug / 缺陷 / 报错 / 不对），或 `下一步` 为「开发执行（修复）」 | 修复 |
| 4 | 无已完成记录，且请求是实施任务包 | 首次实施 |
| 5 | 信号冲突（如已有完整记录却要求推翻重做）或无法确定 | **停下询问** |

修复模式的缺陷来源：`评审报告.md` 最新一轮仍为「待修复 / 部分修复 / 未修复」的问题（`REV-xxx`），或用户消息中的缺陷描述（可含报错、日志片段）。用户手写的报告格式不限，通读提取编号、位置、问题描述；没有编号时自编并在记录中给出对应关系。

## 2. Phase 0 —— 读取

1. 首次实施：读 `1-任务声明.md`，提取下表字段。修复：读评审报告或缺陷描述，以及既有实施记录。
2. 读规则链：项目根和代码根到目标目录逐级的 `AGENTS.md`（及其引用的规则文件），全部阅读；读取 `## dev-flow` 小节（如有）。

| 字段 | 缺失处理 |
| --- | --- |
| 代码根 / 目标工程 | **阻断**：向用户索取，不猜 |
| 授权修改文件 | **阻断**：没有明确边界不进入 Phase 3 |
| 当前基线（哈希 / commit） | 快照当前状态，记录注明无基线可比 |
| 权威资料清单与哈希 | 跳过漂移检查，注明 |
| 静态验收标准 | 只跑通用检查，注明未逐条核对 |
| 禁止修改 / 禁止操作 | 用本文 §6 护栏 |
| 暂停条件 | 用本文 §7 通用暂停条件 |
| 必须保留的行为 | 由 Phase 2b 识别的相邻功能推断，注明为推断 |

冲突裁决优先级：用户指令 > 规则链 > 技术方案 > 任务声明 > 方案片段 > 现有源码 > 原始需求。

3. 首次实施：明确告诉用户「生成任务包 ≠ 已实施」，输出提取结果回显：

```text
代码根：<路径>（版本控制：git / 无）
授权修改文件：<N 个，逐条列出>
验收标准：<M 条，逐条列出>
禁止项：<...>
未识别字段及采用的默认：<...>
待确认的设计决策：<Phase 2b 暴露的歧义>
```

Phase 2a/2b 未发现漂移、冲突、歧义或待裁决的设计决策（或发现的问题均已按门禁确认）时，自检通过：把回显写入「待确认事项」并标「自动通过（自检）」后进入 Phase 3；否则停止等待确认。

## 3. Phase 1 —— 实施前门禁

按 `任务状态.md` 的 `版本控制` 走对应路径，然后执行 `## dev-flow` 小节的 preflight 步骤及 AGENTS.md 正文中的同步要求；任一步失败即停。

**git**：

- 检查当前分支、远端和工作区；识别与本任务无关的已有改动并全程保护（不读、不写、不提交）。
- 有上游时 `git fetch` 后只做安全快进；分叉、冲突、无法快进时停止报告。没有上游时跳过 fetch，并在记录中注明。
- 首次实施：在状态文件「产物」写「开发基线」行：`<分支> @ <HEAD SHA>，上游 <远端/分支> @ <SHA>|无上游，<时间>`。修复轮次不改写该行。

**非 git**：

- 把本轮将要修改的授权文件复制到 `<任务目录>/基线快照/轮次<E>/`（E 为本次实施轮次），保留相对代码根的路径，并记录每个文件的 SHA-256。评审和提交阶段依赖这些快照。
- 首次实施：「开发基线」行写 `非 git，基线快照/轮次1/，<时间>`。

## 4. Phase 2 —— 复核与审查（只读）

**2a 基线复核**：对授权文件逐个计算 SHA-256、编码、换行风格（LF/CRLF）、BOM、结尾换行，与任务声明记录比对；权威资料也比对哈希以发现上游漂移。修复模式改为对比上一轮记录的「修改后哈希」，不一致先查清来源。哈希漂移不等于禁止实施，但必须重新阅读变化内容、重新定位代码锚点，不得套用旧行号。

**2b 审查（STOP 门禁，发现任一问题就停下报告，等确认；确认者见 state-file.md「确认门禁」）**：

首次实施：

| 检查 | 不通过 |
| --- | --- |
| 授权文件在代码根中实际存在 | 路径失效 |
| 基线哈希 / 代码锚点与当前代码一致 | 已漂移，需重新定位 |
| 任务目标不与规则链冲突 | 碰到禁止项 |
| 任务目标不与技术方案冲突 | 语义矛盾 |
| 任务声明内部自洽 | 需裁决的歧义 |
| 不需触碰禁止范围、改环境映射或启动真实服务/设备 | 需要则停 |
| 权威资料哈希与任务声明一致 | 上游文档已变 |

修复模式（轻量）：缺陷所指的位置和行为在当前代码中仍成立；修复不越出授权范围；多条缺陷之间、缺陷与既有实现之间无矛盾。「疑问」类问题在此澄清（向用户或调用方，确认者见 state-file.md「确认门禁」），不当成缺陷直接改。

## 5. Phase 3–6 —— 实施、检查、记录、收尾

**Phase 3 实施**：只改授权文件，在代码根原地修改，不建工程副本、不用 `tmp/` 工作副本；遵守规则链中的实现规范；保留原编码、换行风格和结构标记（代码生成锚点、区段标记等）。修复模式改动最小，只针对缺陷，不顺手重构。

**Phase 4 静态检查**，每项记录命令、返回码、判定（PASS / FAIL / N/A）、证据位置：

1. 改动文件前后 SHA-256：只有授权文件哈希变化。
2. 编码 / 换行 / BOM / 结尾换行：与基线一致；任务要求改变时点明。
3. 结构完整性：`## dev-flow` 小节「结构标记」的成对计数实施前后相等；没有时至少检查括号配平和明显的区段标记。
4. 语法 / 类型 / lint：用 `## dev-flow` 的 static_check 或 AGENTS.md 中的命令；没有时按工具链线索选：`tsconfig.json` → `npx tsc --noEmit`；`package.json` 有 lint 脚本 → `npm run lint`；Python → `ruff check`（无则 `python -m py_compile <改动文件>`）；`go.mod` → `go vet ./...`；`Cargo.toml` → `cargo check`；C/C++ → `clang -fsyntax-only`（按项目给出的 include 和宏）；都没有则记「无可用静态语法工具」。记录 error / warning 数，区分本次引入与既有；用到的桩、mock、降级参数逐项列出。
5. 生成物 / 依赖一致性：项目有代码生成、schema、lock 文件且给了 `--check` 类命令时执行，否则注明跳过。
6. 改动边界：git 用 `git status --porcelain`、`git diff --stat`、逐文件 `git diff`；非 git 用快照逐文件 `diff -u`。改动只在授权清单内，无关已有改动前后一致。
7. 验收标准逐条核对（首次实施）：每条静态验收标准对应一个检查和证据；无法静态判定的归入边界声明。
8. **边界声明（必写）**：本轮静态检查不能证明目标环境构建、运行时行为、集成、真实设备或服务、性能，以及验收中依赖运行才能判定的条目。

**Phase 5 记录**：

- 首次实施：用 [../assets/实施与静态检查记录模板.md](../assets/实施与静态检查记录模板.md) 生成 A 段 ＋「轮次 1」。
- 实施轮次 E：首次实施为 1，此后每次开发执行取已有记录轮次的下一个编号，与基线快照编号一致；它和 `评审轮次`（完整评审次数）相互独立，不要求相等。
- 修复：追加 `## 轮次 E`，不改 A 段和已有轮次；来源写实际依据，例如「评审报告第 R 轮」（R 为该报告的评审轮次）或「用户缺陷描述」。无书面报告的修复也各占一轮。含缺陷处置表：按编号逐条标 `已修复` / `不修改（理由）` / `延后`。不回写评审报告。
- 只记录实际执行且有证据的项；未执行写「未执行」，**绝不写成 PASS**。静态检查、语法检查、目标环境构建、集成或设备验证、验收测试分开记录。之前标「未执行」的项本轮实际执行了，更新为实际结果。

**Phase 6 收尾**：不提交、不推送、不部署、不启动真实服务或设备。按任务声明的交付物逐项汇报；结论诚实，点明未完成部分（例如「完成代码修改及静态检查，未执行目标环境构建」）。

## 6. 护栏（任何模式都适用）

- 不新建工程副本，不用临时工作副本作为修改基线（`基线快照/` 只作只读比对）。
- 未获授权不执行：提交、推送、部署、打 tag、改 CI 配置；启动/停止真实服务或测量、操作真实设备、发送真实请求或报文。
- 只改授权文件；确实需要改其他文件时，先报告具体原因，经用户同意再扩大范围。
- 与本任务无关的已有改动全程保护。
- 遇到暂停条件：保留已有只读证据和局部差异，停下报告。

## 7. 通用暂停条件（任务声明未自带时使用）

1. 代码根缺失或无法唯一确认。
2. 规则链内部冲突，或规则链与技术方案冲突。
3. 授权文件当前哈希已变且无法确认有效基线。
4. 源码、生成物、配置之间已经不一致，无法确定有效基线。
5. 达成目标必须修改禁止范围、改变环境映射或启动真实服务/设备。
6. 数据语义、接口约定、动作方向等与技术方案冲突。
7. 验收标准之间或与任务目标之间出现新的歧义。
8. git 门禁无法得到干净一致的基线。

## 写入任务状态

- 本阶段不维护开发须知，只写 `任务状态.md`。
- Phase 1 通过后立即写「开发基线」行（首次实施）。
- 回显、Phase 2b 或暂停条件需要裁决：`阶段状态：待用户确认`（或 `阻塞`），问题写入「待确认事项」后停止。
- 记录生成或追加完成：「产物」登记 `开发任务包/实施与静态检查记录.md`（非 git 同时登记 `基线快照/`）；写 `当前阶段：代码评审`、`阶段状态：待执行`、`下一步：代码评审（第 <评审轮次 + 1> 轮）`；历史追加本轮结论。
