# 阶段 5：代码评审

## 目标

独立检查本次代码修改是否符合技术方案和任务声明，核验实施记录与真实差异及证据是否一致。问题写入 `<任务目录>/评审报告.md`；修复后再次评审时保留历史，追加下一轮。

## 使用条件

- 任务目录能唯一确定；只能推断时复述路径。
- 项目已初始化；代码根由规则、方案、任务声明和状态文件一致指向。
- 差异基线可唯一识别（见第 2 节），否则结论只能是「无法完成评审」。

## 边界

- 只读代码；只写 `评审报告.md`、开发须知和 `任务状态.md`。
- 不修改问题代码、不生成实施记录、不提交或推送。
- 不运行会改写工程、部署、调用外部服务、操作数据库或设备、影响外部状态的验证，除非用户明确授权且项目规则允许。
- 静态评审通过不等于构建、运行、集成或目标环境验证通过。

## 必需输入

完整读取：项目根和代码根适用的全部 `AGENTS.md`；开发须知；`技术方案.md`；`开发任务包/1-任务声明.md`、`2-技术方案小节片段.md`、`实施与静态检查记录.md`；当前源码和本次真实差异；已有的 `评审报告.md`（复审时）。

任何必需文档缺失、存在多个候选或指向不同任务时停止。缺少实施记录时不得生成「评审通过」报告；任务条目能唯一定位时，可把开发须知状态记为「证据不足/无法评审」。

## 工作流

### 1. 确定任务、代码根和规则

读取规则链和开发须知，核对项目根、代码根、版本控制、代码基线和任务条目（至少为「任务包已生成、待开发」）。规则冲突、工程不存在、开发须知失真或任务包所指工程与当前不一致时停止询问。

### 2. 确定差异基线

**git**，按优先级：

1. 实施记录和任务声明共同指向的基线提交到当前提交或工作区；
2. 状态文件「开发基线」的 HEAD 到当前工作区（含 staged、unstaged 和相关 untracked）；
3. 尚未提交且无记录基线时，当前 `HEAD` 到工作区，并在报告中说明边界。

**非 git**：以最近一个实施轮次的 `基线快照/轮次<E>/` 为旧版本、代码根当前文件为新版本做 `diff -u`；复审时本轮差异以该快照为准，整体差异以轮次 1 快照为准。快照缺失或哈希与实施记录不符时停止。

通用：不按修改时间推断基线；不为查看差异而 checkout、reset、stash、clean 或切换分支；开发须知的代码基线只用于定位，必须与方案、任务声明、实施记录交叉核对。无法唯一确定基线时停止，不把整个工程当作本次修改。

评审范围 = 真实差异 ∩ 任务声明授权范围。对每个修改文件分类：任务内且已记录（正常评审）；任务内但未记录（记录不一致，仍评审代码）；记录声称修改但无差异（记录不一致）；授权范围外（单列，判断是否为未授权改动或用户已有改动）；无法判定归属（不擅自归入，报告证据缺口）。不用 `git add -A` 等写操作整理范围。

### 3. 核对实施记录

记录既是输入也是被核验对象，不把自述当事实：

| 记录声明 | 独立证据 |
| --- | --- |
| 修改文件 / 方法 | 真实差异和当前源码 |
| 修改前后哈希 | 实际哈希、git 对象或快照 |
| 调用关系 | 全文符号搜索和调用点 |
| 静态检查通过 | 命令、日志或安全复跑结果 |
| 构建通过 | 对应平台、工具链和完整输出 |
| 运行 / 集成 / 目标环境通过 | 对应环境的原始证据 |

还要检查：未记录的修改、删除或生成文件变化；偏差、风险和遗留事项是否披露；未执行的验证是否被写成通过。安全、只读的静态检查可以复跑，结果与记录分开标明；不能复核的写「未能独立验证」。

### 4. 评审代码

至少核对：完整技术方案的总体约束和跨方法设计；方案片段中的方法流程、边界、关键决策和依赖；任务声明的范围和自检要求；实现的调用路径、状态初始化与清理、返回值、错误、超时、取消、重复调用和重入；项目 `AGENTS.md` 声明的专项结构、同步规则和 `## dev-flow` 检查项；是否引入编译错误、接口错误、越界、状态泄漏、错误文件修改或回归。

只启用当前项目规则中实际存在的专项检查，不套用其他技术栈的结论。

### 5. 记录问题

每个问题用稳定编号 `REV-001`、`REV-002`……，一个问题只对应一个根因，指向最精确的位置：

```markdown
### REV-001：[问题标题]

- 严重程度：P1
- 状态：待修复
- 技术方案：第 X 节
- 任务声明：第 Y 节
- 文件与位置：path/to/file:line
- 当前实现：
- 预期实现：
- 触发条件：
- 影响：
- 判断依据：
- 修改建议：
- 复审要点：
```

严重程度按影响和可触发性定，不因好改而降级：

- P0：安全事故、不可恢复的数据损坏、交付到错误工程等灾难性影响；
- P1：核心功能、接口、状态机、编译或关键需求错误；阻止通过；
- P2：明显风险、遗漏、异常路径错误、实施记录重要不一致、较高概率回归；
- P3：非阻断的可维护性或清晰度建议。

### 6. 首轮报告

输出 `<任务目录>/评审报告.md`，可采用 [../assets/评审报告模板.md](../assets/评审报告模板.md)。至少包含：评审输入、基线与范围、总体结论、问题、方案符合性、任务声明符合性、实施记录一致性、范围外修改、实际执行的检查、证据边界和未执行验证。

结论类型：

- **评审通过**：没有 P0/P1，所有必须整改的问题已修复。只能写「本次静态评审未发现阻断问题」，不声称已经在运行或目标环境中验证。
- **有条件通过**：只剩已接受（用户或调用方）或任务允许保留的非阻断项。
- **评审不通过**：存在 P0/P1、关键要求未实现，或证据与实现明显矛盾；有尚未接受的 P2 时按风险判断为不通过或有条件通过。
- **无法完成评审**：缺少必需文档、差异基线、源码或关键证据。

证据等级分开陈述（只列项目适用的）：源码与配置静态事实；文本、结构、格式与符号检查；本地语法或替代工具链检查；目标平台构建；软件运行；集成与外部交互；目标设备或生产环境行为。低等级不能证明高等级；只有摘要没有原始输出的日志只能作为线索。

### 7. 复审

1. 完整读取已有报告，保留所有内容和编号。
2. 确定上一轮基线、本轮新差异和最新实施记录；记录未同步更新时指出。
3. 逐项复核「待修复 / 部分修复 / 无法验证」的问题，更新为「已修复」（触发路径已消除、回归点已查）、「部分修复」、「未修复」或「无法验证」，写明证据；不删除、不重编号、不改写旧问题。
4. 检查修复是否引入新问题；新问题用最大编号加一，旧问题再次出现时更新原编号。
5. 在报告末尾追加：

```markdown
## 第N轮评审

### 复审基线
### 既有问题复核
| 问题编号 | 上轮状态 | 本轮状态 | 证据与结论 |
| --- | --- | --- | --- |
### 本轮新增问题
### 本轮实施记录一致性
### 本轮结论
```

6. 定向复审只证明指定问题的状态；只有原完整评审范围仍然有效、所有阻断问题已关闭、修复没有引入范围外差异时，才能把任务整体标为通过，否则开发须知标「定向复审完成」及未覆盖范围。

### 8. 维护开发须知

报告写入后，更新开发须知中的唯一任务条目：

| 评审结果 | 任务状态 | 当前实现区 |
| --- | --- | --- |
| 无法完成评审 | `证据不足/无法评审` | 不改 |
| 评审不通过 | `待修复` | 不把计划设计提升为实现 |
| 有条件通过 | `有条件通过` | 只写有证据支持的实现，注明剩余条件 |
| 评审通过 | `评审通过、待提交` | 按真实差异更新功能、算法、接口、进度和验证边界 |

- 加入方案、任务声明、方案片段、实施记录和评审报告的相对链接。
- 评审通过时用最终真实实现覆盖过时描述，不追加互相矛盾的版本。
- 未提交时记录评审基线、工作区状态或文件哈希，不猜测最终 commit。
- 构建、运行、集成、目标环境验证没有证据时继续列为待验证。
- 不改写本轮差异之外的既有功能描述。

用户在评审后自行提交并要求登记时：只读核对提交属于同一代码根、提交差异与已评审差异一致；一致则只更新开发须知代码基线和状态为「已提交 / 已推送」；混入未评审代码或评审后又有语义修改时，要求重新评审。

## 写入任务状态

报告写入、开发须知更新后，先处理轮次：评审完整完成时把 `评审轮次` 加 1（每次评审只加这一次），更新后的值记为 N，即本轮是第 N 轮评审；无法完成评审时不加。再按结论写入：

- **评审不通过**：`当前阶段：开发执行`、`下一步：开发执行（修复，针对第 N 轮评审）`。阶段状态按以下顺序判定：
  1. N ≥ 3（评审三轮保护，优先）：`阶段状态：待用户确认`，「待确认事项」登记「评审已完成 N 轮仍不通过，请确认继续按报告修复、调整方案或停止」，附阻断问题编号摘要；只能由用户确认，无论 `评审不通过后` 如何设置。
  2. `评审不通过后：停下确认`（缺少该字段时同此）：`阶段状态：待用户确认`，「待确认事项」登记「确认按第 N 轮评审报告修复」，附阻断问题编号摘要；只能由用户确认。用户回复「修复评审问题」等明确同意即视为确认；也可以指定只修部分问题或改变处理方式，原话写入该事项。
  3. `评审不通过后：直接修复`：`阶段状态：待执行`。
- **评审通过，git**：`当前阶段：提交`、`阶段状态：待用户确认`；「待确认事项」登记「确认提交（见「提交确认材料」）」；在「提交确认材料」写已评审文件及当前 SHA-256、当前分支及上游（无上游时写明「将只提交不推送」）、提交说明草稿（格式见 stage-6）。提交确认是**必停门禁**，不得自动通过。
- **评审通过，非 git**：`当前阶段：提交`、`阶段状态：待执行`；「提交确认材料」写已评审文件及当前 SHA-256。
- **有条件通过**：同评审通过，且待确认事项中单独列出剩余条件，请用户或调用方接受（非 git 时也为 `待用户确认`）；git 时提交确认仍单独由用户确认。
- **无法完成评审**：`阶段状态：阻塞`，写明缺失的文档、基线或证据。
- 「产物」登记 `评审报告.md`；历史追加本轮结论。
