# 阶段 6：提交

## 目标

按 `任务状态.md` 的 `版本控制` 收尾：

- **git**：用户确认后只提交已评审文件；当前分支有上游就推送，没有上游只提交。然后登记代码基线。
- **非 git**：不提交，核对文件未被改动后把文件哈希登记为代码基线。

## 前提

- 代码评审阶段已把确认材料写入「提交确认材料」：已评审文件及 SHA-256；git 时还有分支、上游和提交说明草稿。本阶段不重复准备，不重读规则链全文。
- git 时，远端基线已在开发执行 Phase 1 记录为「开发基线」，本阶段不再 fetch；远端有新提交时 `git push` 会被拒，此时停下。
- **git 的提交确认是必停门禁**：「确认提交」已标 `已确认`，或用户本次明确确认，才执行。手动和 herdr 调度都一样。

## 边界

- 只提交已评审文件；不用 `git add -A` / `git add .`；与本任务无关的改动不读、不写、不提交。`AGENT_WorkSpace/` 下的文档只有在项目 AGENTS.md 要求时才一并提交。
- 不 force push、不改写历史、不打 tag、不 merge / rebase、不切换分支、不 stash / clean、不设置上游。
- 不因提交成功补写任何未执行的构建、运行、集成或设备验证结论。
- 项目 AGENTS.md 对提交或推送另有约定（如禁止推送、指定说明格式）时，以其为准。

## 工作流

### 1. 核对已评审文件未被改动（两种情况都做）

逐个计算已评审文件的 SHA-256，与「提交确认材料」比较。有任何不一致（评审后被修改或被工具回写）就停止：状态退回 `代码评审 / 待执行`，写明哪个文件变了。

### 2. 非 git：登记并结束

跳到第 5 步；代码基线写「非 git：已评审文件 SHA-256 见任务状态」。

### 3. git：暂存并提交

```bash
git add -- <已评审文件…>
git diff --cached --stat        # 确认暂存区只有已评审文件
git commit -F <提交说明临时文件>
```

- 使用已确认的草稿；用户改过的以用户版本为准。用临时文件传入，避免 shell 转义破坏多字节字符和换行。
- 当前 agent 环境要求署名行时追加在末尾。
- 说明格式按项目 AGENTS.md 约定；没有约定时用：

```text
<任务名称>：<一句话变更摘要>

变更内容：
- <主要改动>

技术方案：AGENT_WorkSpace/<任务目录>/技术方案.md
评审结论：第 N 轮评审通过（AGENT_WorkSpace/<任务目录>/评审报告.md）
验证边界：<已执行的静态检查>；未执行：<构建 / 运行 / 集成等>
```

### 4. git：推送

先判断上游：`git rev-parse --abbrev-ref --symbolic-full-name @{u}`。

- **有上游**：`git push`。成功时，输出中的 `<旧>..<新>  <分支> -> <分支>` 就是推送证据。被拒、鉴权或网络失败：保留本地提交，停止并报告错误原文，不自动 pull / merge / rebase。
- **无上游**：不推送，记录「已提交、未推送（无上游）」。

### 5. 登记

`开发须知.md` 只改两处，其他章节不动：

1. 文件头「当前代码基线」→ git：新提交 SHA（推送失败时注明「本地已提交、未推送」）；非 git：见第 2 步。
2. 「重要改动索引」中本任务条目 → 状态「已推送」「已提交」或「已完成（非 git）」，git 时附提交 SHA。

## 写入任务状态

- 成功（推送成功、无上游只提交、或非 git 登记完成）：「产物」登记提交 SHA 和分支（非 git 不填）；`当前阶段：完成`、`阶段状态：已完成`、`下一步：无`；历史追加一行，注明是否推送。
- 有上游但推送失败：`当前阶段：提交`、`阶段状态：阻塞`，「产物」登记本地提交 SHA，`下一步：推送（解决阻塞后）`。
- 第 1 步发现文件被改：退回 `代码评审 / 待执行`。
