# 任务状态.md —— 格式与状态迁移

## 位置与职责

```text
<项目根>/AGENT_WorkSpace/<开发任务名称>/任务状态.md
```

- 只记录流程状态：阶段、阶段状态、下一步、代码根与版本控制、分工、待确认事项、产物链接（含开发基线、提交 SHA）、提交确认材料、历史。不写方案、实现、评审内容本身。
- 表格单元格保持简短；较长内容（如提交说明草稿）放到对应小节，表格里只引用。
- 在「技术方案」阶段随任务目录一起创建（模板 [../assets/任务状态模板.md](../assets/任务状态模板.md)）；项目初始化阶段没有状态文件。
- 可能由不同 agent 或调度者写入。每次写入前重新读取整个文件，只修改本次负责的字段，不覆盖他人写入的分工与确认记录。
- 调度者只写调度信息（阶段分工、调度方式、调度者、调度模式、调度起始评审轮次、派发记录）和「待确认事项」中的用户答复；阶段执行者写其余字段。
- 旧状态文件缺少 `代码根` 或 `版本控制` 时，下一次写入的阶段按 SKILL.md「版本控制判定」补上。

## 字段

| 字段 | 取值 |
| --- | --- |
| 项目根 | 绝对路径 |
| 代码根 | 绝对路径；与项目根相同时也写出 |
| 版本控制 | `git（<仓库根>）` / `无` |
| 当前阶段 | `技术方案` / `任务包` / `开发执行` / `代码评审` / `提交` / `完成` |
| 阶段状态 | `待执行` / `待用户确认` / `阻塞` / `已完成` |
| 下一步 | 阶段名 ＋ 模式，如 `开发执行（修复，轮次 2）`、`代码评审（第 2 轮）`、`用户确认技术方案` |
| 评审轮次 | 已完成的评审轮数，初始 `0` |
| 调度方式 | `手动` / `herdr` |
| 调度者 | herdr 调度时：`<kind>（<pane_id>）`；手动时留空 |
| 调度模式 | `单步` / `全流程`（herdr 调度时） |
| 调度起始评审轮次 | 开始本次调度时的评审轮次，用于修复循环上限 |
| 派发记录 | 最近一次派发：`<阶段> → <pane_id>，YYYY-MM-DD HH:MM` |
| 更新时间 / 更新者 | `YYYY-MM-DD HH:MM` / agent 名（如 `claude`、`codex`）或 `用户` |

「当前阶段」表示**下一个要执行或正在等待的阶段**。一个阶段做完后，执行者直接把「当前阶段」推进到下一阶段并置 `待执行`（或 `待用户确认`），因此「当前阶段 ＋ 阶段状态」即可决定本次动作。

## 状态迁移

| 当前阶段 / 阶段状态 | 条件 | 本次动作 → 写入 |
| --- | --- | --- |
| （未初始化） | — | 项目初始化 → 不写状态文件 |
| （已初始化，无该任务目录） | 用户提出需求并要求设计方案 | 技术方案 → `技术方案 / 待用户确认` |
| 技术方案 / 待用户确认 | 用户确认 | 更新方案与开发须知为「设计已确认、待开发」→ `任务包 / 待执行` |
| 技术方案 / 待用户确认 | 用户要求修改 | 修改方案 → 仍 `技术方案 / 待用户确认` |
| 任务包 / 待执行 | — | 生成任务包 → `开发执行 / 待执行`（首次实施） |
| 开发执行 / 待执行 | — | 实施或修复 → `代码评审 / 待执行` |
| 代码评审 / 待执行 | 评审不通过 | → `开发执行 / 待执行`（修复，轮次 +1），评审轮次 +1 |
| 代码评审 / 待执行 | 通过 / 有条件通过，git | → `提交 / 待用户确认`（**必停**），评审轮次 +1 |
| 代码评审 / 待执行 | 通过，非 git | → `提交 / 待执行`，评审轮次 +1 |
| 代码评审 / 待执行 | 有条件通过，非 git | → `提交 / 待用户确认`（确认接受剩余条件），评审轮次 +1 |
| 代码评审 / 待执行 | 无法完成评审 | → `代码评审 / 阻塞` |
| 提交 / 待用户确认 | 用户确认 | git：提交（有上游时推送）并登记；非 git：登记 → `完成 / 已完成` |
| 提交 / 待执行 | 非 git，或 git 且确认已由调度者写入 | 同上 |
| 任一 / 待用户确认 | 待确认事项已「已确认」或用户本次确认 | 按该阶段继续 |
| 任一 / 阻塞 | 用户给出处理方式并写入待确认事项 | 按该阶段重新执行 |

## 确认门禁

| 门禁 | 手动调用 | herdr 调度 |
| --- | --- | --- |
| 技术方案确认 | 必停 | 必停 |
| 任务包定位确认 | 必停 | 无矛盾、路径与方法清单唯一时自动通过并记录 |
| 任务包方案矛盾口径 | 必停 | 必停 |
| 开发执行 Phase 0 回显 | 必停 | Phase 2a/2b 无漂移、冲突、歧义时自动通过并记录 |
| 开发执行 Phase 2b 问题 / 暂停条件 | 必停 | 必停 |
| 评审有条件通过的剩余条件 | 必停 | 必停 |
| 提交确认（git） | 必停 | 必停 |

自动通过时在「待确认事项」写一行：状态 `自动通过（herdr 调度）`，用户答复列写 `—`，问题列写回显或定位摘要。

## 一致性规则

- `任务状态.md` 管流程阶段；`开发须知.md` 的任务条目由方案、任务包、评审、提交阶段维护，开发执行不写。
- 两者冲突（例如状态文件在「开发执行」，开发须知仍为「方案待确认」），或状态文件与实际产物不符（例如记为「代码评审」但没有实施记录）：停止报告，不静默修正。
- 用户请求中点名的阶段与状态文件不一致：停止报告。
- 未完成任务 = 「当前阶段」不是 `完成` 的任务。
