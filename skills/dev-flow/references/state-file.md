# 任务状态.md —— 格式与状态迁移

## 位置与职责

```text
<项目根>/AGENT_WorkSpace/<开发任务名称>/任务状态.md
```

- 只记录流程状态：阶段、阶段状态、下一步、代码根与版本控制、待确认事项、产物链接（含开发基线、提交 SHA）、提交确认材料、历史。不写方案、实现、评审内容本身。
- 表格单元格保持简短；较长内容（如提交说明草稿）放到对应小节，表格里只引用。
- 在「技术方案」阶段随任务目录一起创建（模板 [../assets/任务状态模板.md](../assets/任务状态模板.md)）；项目初始化阶段没有状态文件。
- 可能由不同 agent 写入。每次写入前重新读取整个文件，只修改本次负责的字段，不覆盖他人写入的确认记录。
- 不记录调度信息（由谁派发、派给谁、分工）。旧状态文件中已有的调度相关字段和「阶段分工」表忽略，不读、不改、不删。
- 旧状态文件缺少 `代码根` 或 `版本控制` 时，下一次写入的阶段按 SKILL.md「版本控制判定」补上。

## 字段

| 字段 | 取值 |
| --- | --- |
| 项目根 | 绝对路径 |
| 代码根 | 绝对路径；与项目根相同时也写出 |
| 版本控制 | `git（<仓库根>）` / `无` |
| 当前阶段 | `技术方案` / `任务包` / `开发执行` / `代码评审` / `提交` / `完成` |
| 阶段状态 | `待执行` / `待用户确认` / `阻塞` / `已完成` |
| 下一步 | 阶段名 ＋ 模式，如 `开发执行（修复，针对第 1 轮评审）`、`代码评审（第 2 轮）`、`用户确认技术方案` |
| 评审轮次 | 已完整完成的评审次数，初始 `0`；与实施记录、基线快照使用的实施轮次相互独立，不要求相等 |
| 评审不通过后 | `停下确认`（默认）/ `直接修复`；只按用户明确指示设置或修改；旧状态文件缺少该字段时按 `停下确认`；`直接修复` 受评审三轮保护约束 |
| 更新时间 / 更新者 | `YYYY-MM-DD HH:MM` / agent 名（如 `claude`、`codex`）或 `用户` |

「当前阶段」表示**下一个要执行或正在等待的阶段**。一个阶段做完后，执行者直接把「当前阶段」推进到下一阶段并置 `待执行`（或 `待用户确认`），因此「当前阶段 ＋ 阶段状态」即可决定本次动作。

## 状态迁移

| 当前阶段 / 阶段状态 | 条件 | 本次动作 → 写入 |
| --- | --- | --- |
| （未初始化） | — | 项目初始化 → 不写状态文件 |
| （已初始化，无该任务目录） | 用户提出需求并要求设计方案 | 技术方案 → `技术方案 / 待用户确认` |
| 技术方案 / 待用户确认 | 用户确认 | 更新方案与开发须知为「设计已确认、待开发」→ `任务包 / 待执行` |
| 技术方案 / 待用户确认 | 用户要求修改 | 修改方案 → 仍 `技术方案 / 待用户确认` |
| 任务包 / 待执行 | — | 生成任务包 → `开发执行 / 待执行`（首次实施） |
| 开发执行 / 待执行 | — | 实施或修复 → `代码评审 / 待执行` |
| 代码评审 / 待执行 | 评审不通过，更新后的评审轮次 ≥ 3（优先于下两行） | → `开发执行 / 待用户确认`（评审三轮保护，只能用户确认） |
| 代码评审 / 待执行 | 评审不通过，`停下确认` | → `开发执行 / 待用户确认`（确认按评审报告修复） |
| 代码评审 / 待执行 | 评审不通过，`直接修复` | → `开发执行 / 待执行`（修复） |
| 代码评审 / 待执行 | 通过 / 有条件通过，git | → `提交 / 待用户确认`（**必停**） |
| 代码评审 / 待执行 | 通过，非 git | → `提交 / 待执行` |
| 代码评审 / 待执行 | 有条件通过，非 git | → `提交 / 待用户确认`（确认接受剩余条件） |
| 代码评审 / 待执行 | 无法完成评审 | → `代码评审 / 阻塞` |
| 提交 / 待用户确认 | git：用户已确认提交，且剩余条件（如有）已按门禁接受 | 提交（有上游时推送）并登记 → `完成 / 已完成` |
| 提交 / 待用户确认 | 非 git：剩余条件已由用户或调用方接受 | 登记 → `完成 / 已完成` |
| 提交 / 待执行 | 非 git | 登记 → `完成 / 已完成` |
| 任一 / 待用户确认 | 待确认事项已「已确认」或本次明确确认，且确认者符合门禁表 | 按该阶段继续 |
| 任一 / 阻塞 | 处理方式已写入待确认事项，确认者符合门禁表；缺失的文档、基线或证据已实际补齐（不能只凭一句确认放过） | 按该阶段重新执行 |

## 确认门禁

门禁规则不区分由谁调用、是否由调度工具派发：

| 门禁 | 规则 | 确认者 |
| --- | --- | --- |
| 技术方案确认 | 必停 | 用户 |
| 任务包定位确认 | 自检通过（路径与方法清单唯一、方案已确认、无矛盾或矛盾口径已确认）时自动通过并记录；否则停 | 用户或调用方 |
| 任务包方案矛盾口径 | 停 | 用户或调用方 |
| 开发执行 Phase 0 回显 | 自检通过（Phase 2a/2b 无漂移、冲突、歧义、待裁决设计决策，或发现的问题均已确认）时自动通过并记录；否则停 | 用户或调用方 |
| 开发执行 Phase 2b 问题 / 暂停条件 | 停 | 用户或调用方 |
| 评审不通过后进入修复 | `评审不通过后：停下确认`（默认）时停；`直接修复` 时不停 | 用户 |
| 评审三轮保护 | 评审不通过且更新后的评审轮次 ≥ 3 时，无论 `评审不通过后` 如何设置都停 | 用户 |
| 评审有条件通过的剩余条件 | 停 | 用户或调用方 |
| 提交确认（git） | 必停 | 用户 |

- 「停」的门禁在对应待确认事项标 `已确认`，或本次消息明确确认后继续。确认者为「用户」的门禁，事项中必须记录用户原话；调用方不得代为确认。
- 「确认者 / 答复原文」列写 `用户：<原话>` 或 `<调用方 agent 名>：<决定>`。
- 自动通过时在「待确认事项」写一行：状态 `自动通过（自检）`，答复列写 `—`，问题列写回显或定位摘要。
- 评审三轮保护：确认继续修复只授权下一轮开发执行与评审，不修改 `评审不通过后` 字段；之后评审仍不通过时再次停下。没有总评审次数上限。
- 旧状态文件停在 git 的 `提交 / 待执行` 时：「确认提交」事项记录了用户原话的，按阶段 6 执行；否则改为 `提交 / 待用户确认` 并停下。旧调度字段不作为授权依据。

## 一致性规则

- `任务状态.md` 管流程阶段；`开发须知.md` 的任务条目由方案、任务包、评审、提交阶段维护，开发执行不写。
- 两者冲突（例如状态文件在「开发执行」，开发须知仍为「方案待确认」），或状态文件与实际产物不符（例如记为「代码评审」但没有实施记录）：停止报告，不静默修正。
- 用户请求中点名的阶段与状态文件不一致：停止报告。
- 未完成任务 = 「当前阶段」不是 `完成` 的任务。
