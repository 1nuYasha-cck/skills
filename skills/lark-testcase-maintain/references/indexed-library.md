# 索引库（schema_profile=indexed）

适用于已有的“正式索引 + 维护台账”云端库。标准三表库行为不变；本模式只在库配置写 `schema_profile: "indexed"` 时启用，实现在 `scripts/indexed.py`。

## 配置

`kind` 仍为 `standard`。`tables` 为表键到 table_id：必需 catalog（分类目录）、cases（正式索引）、sources（来源原件）、batches（批次）、review（入库前审核）；可选 issues（问题，只读核对/导出）、routes（分表路由，校验当前索引表已启用且未超 `目标记录上限`）。

- `table_base_tokens`：`{表键: base_token}`，未列出的表用 `base_token`；允许索引与台账分属不同 Base。
- `field_maps`：`{表键: {规范字段名: 真实字段名}}`，缺省不映射。规范字段清单见 `indexed.FIELDS`；未知规范名或重复目标报错。导出/报告同时给出真实字段（`fields`）、逻辑字段（`logical`）与定位（`locator`：base、table、record）。
- `search_policy.publication_field / published_values[0]`：发布写入的字段和值，缺省 `发布状态 / 已发布`。
- `folders.originals / bodies`：原件与正文分卷目录。
- `maintain`（仅本 Skill 使用）：`web_url` 为租户源站（如 `https://<tenant-domain>`），发布链接只由它和真实 token/record_id 拼接，缺失时 publish 直接拒绝，不猜测；`catalog_doc` 正文目录；`browse.view / full_view / fields` 普通浏览视图；`volume.max_cases / max_chars` 分卷阈值；`navigation_headings` 文档中已有导航区标题，新章节插在其前；`values` 可覆盖选项词汇（见 `indexed.VALUES`）。

所有写命令先读字段并校验类型与选项，缺字段、错类型、缺选项或占位符时零写入。

## 导入：归档与待审核

`import` 计划格式同 [导入计划](import-plan.md)，`targets.base` 必须为 true（正文由发布写）。额外可选：用例 `系统用例ID`（指定则修订该用例）、`待确认项`（字符串数组），计划级 `allow_duplicate_display_ids`。

- 原件按 SHA-256 复用来源记录，否则上传并登记 sources；登记批次后在 review 写待审核/未入库行，读回校验后结束批次。不写索引、目录或正文：**保存≠发布**。
- 系统用例ID 与原编号分离：未指定时由原件 SHA、原编号和来源位置派生（重跑幂等）。原编号已被其他系统ID使用时报冲突、不覆盖；确为新用例时列入 `allow_duplicate_display_ids`。
- 修订：同 ID 内容或元数据变化即新建下一 `内容版本` 的审核行（旧行保留），`on_conflict=skip/fail` 分别跳过/冲突。
- 计划内同一原编号也须列入 `allow_duplicate_display_ids`，且来源位置不同（派生出不同系统ID），否则报错/冲突。
- `提交键` 绑定整份发布输入：系统用例ID、内容版本、来源ID、来源文件链接、导入批次ID、待确认项、两个哈希，以及整份 `结构化用例` JSON 的摘要（含完整用例的来源文件/来源位置、写入目录的分类路径/说明/关键词、来源追溯与说明）；`结构化用例.identity` 保存同一份身份。不新增表字段。
- 重复导入幂等：内容、元数据、待确认项与发布输入（用例、分类、来源追溯）均相同才算未变；来源位置或分类信息变化生成新版本，需重新审核。
- 审核行写 `内容哈希`（标题、前置、步骤、预期、需求、测试类型、设计方法、状态、扩展字段）和 `元数据哈希`（原编号、分类、项目/模块/功能、优先级、版本、关键词、摘要），完整标准用例与来源追溯存于 `结构化用例`。

## 人工审核

人在 review 表把最新版本改为 `审核通过` 并填审核人、审核时间。发布时从 Base 重新读取：状态非通过、缺审核人/时间、当前行重算哈希与提交哈希不符（审核后改动内容）、`审核绑定*哈希` 已填但不符、重算 `提交键` 不符（审核后改了系统ID、版本、来源、批次或待确认项）、`结构化用例.identity` 与列不符，都拒绝发布并给出原因。内容需改时重新导入生成新版本，再审核。

可信边界：只有本 Skill 当前哈希方案（`结构化用例.hash_scheme`，当前为完整绑定的 `maintain-indexed-3`）写入的审核行可重算并发布；旧方案行即使内容相同，重新导入也生成新版本待审核。历史行（含已发布的存量）只在 check 中计数，不重算、不补绑定、不视为重新审核；需要变更时以 `系统用例ID` 重新导入生成新版本，由人重新审核后发布。

## 发布

```bash
python3 scripts/maintain.py publish --config <配置> --library <库名> --out <报告> [--plan <发布计划>] --dry-run
python3 scripts/maintain.py publish --config <配置> --library <库名> --out <另一报告> [--plan <发布计划>]
```

发布计划可选，只允许 `{"publish_version":"1.0","library":"…","system_ids":[…],"note":"…"}`；不得携带审核状态。缺省发布所有最新版本未入库的用例。

顺序：登记发布批次 → 新用例先建 `发布状态=待审核` 的索引暂存行（取得 record 链接，正式检索不可见）→ 逐条插入正文章节并回读定位 → 校验原有锚点与导航标题未丢失 → 重读审核行，期间被改动的不发布 → 补分类目录 → 更新索引为已发布并写正文链接/文档token/章节block ID/文档版本 → 同步该分卷全部索引行的 `文档版本` → 审核行置已入库并写正式索引链接 → 读回。

- 正文不覆盖整卷：修订在原分卷新增“编号 标题（内容版本 n）”章节，旧章节与锚点保留；新用例进入同项目/模块/功能的最后一卷。`max_cases`、`max_chars` 是分卷硬上限：前者按分卷中实际存在的用例章节数（含保留的历史版本）计，后者按插入后的预计正文长度计；新增或修订放不下时写入下一卷（修订的旧章节与锚点留在原卷），已有同名分卷若已满不覆写、改用下一编号。单条章节本身超过 `max_chars` 时拒绝发布，绝不切分。新卷链接追加到正文目录。
- 章节身份：标题为可读的“原编号 标题（内容版本 n）”，不含系统ID，可以重复；章节身份以其正文中指向**唯一索引记录 URL**（`<web_url>/base/<base>?table=<table>&record=<record_id>`）的回链为准，标题只用于核对版本。写入结果未知后的复用、发布读回和 check 都要求“标题+本记录回链”恰好命中一个章节，绝不复用其他记录的同名章节。跨 Skill 核验（如 Search）也应以索引记录 URL 回链确认身份。
- 双向链接：章节含“返回用例索引（编号）”“返回检索浏览”“返回正文目录”；索引 `正文链接` 为 `[编号 标题](分卷#章节)`。技术ID只留在数据，不出现在正文。未配置浏览视图或目录时省略该链接并在 `missing_navigation_config` 报告。
- 任一正文写失败即停止，失败分卷的用例不发布；结果未知只读回确认、不重发；只有同标题、回链本记录且正文与审核内容一致（忽略 XML 规范化、块 id 与导航链接段）的章节才视为上次未知写入已成功并复用；回链一致但正文被改动时报 `section_conflict` 停止，不认领、不覆盖。重跑会复用暂存行和同名分卷。
- 台账补齐：索引已发布同一版本且哈希一致、但审核行未入库（如上次审核行更新失败）时，先确认当前审核仍有效、正文章节可由标题+回链唯一定位且与索引锚点一致、章节正文与审核内容一致，写台账前再重读审核行并比较完整绑定，然后幂等补写审核行入库状态与链接；审核被撤回或变化时只报告，不补写、不撤销已发布索引。

## 浏览视图

`browse-view --config --library --out [--dry-run]`：读字段和视图，仅对 `maintain.browse.view` 设置完整可见字段列表（顺序即配置）；拒绝技术字段、未知字段或与 `full_view` 相同；不删除字段，不修改完整字段视图，只报告其是否覆盖全部字段。

## 核对与导出

`check` 读取全部注册表和被引用正文：重复/空系统ID、已发布行缺正文链接或锚点、链接锚点与 `章节block ID` 不符、多条索引记录共用一个章节、本 Skill 格式章节未回链本记录、版本与索引不符或正文与审核内容不符（历史章节只要求文档内有回链）、已发布版本无审核行或未通过或哈希不同、正文缺锚点或缺回到 record 的链接、`文档版本` 与正文 revision 不符、审核后改动、路由问题。重复原编号和历史哈希行列在 `info`。任一表或正文读失败为 partial。`export` 输出各注册表 ndjson（含 logical 与 locator）、被引用正文 `body-NNNN.xml` 与 manifest，读不全标 partial。
