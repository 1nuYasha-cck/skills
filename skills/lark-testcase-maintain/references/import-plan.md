# Agent 导入计划

```json
{
  "plan_version": "2.0",
  "library": "示例用例库",
  "batch": {"name": "首次导入", "source_file": "<用户指定来源文件>", "note": "梳理说明"},
  "targets": {"base": true, "doc": true},
  "on_conflict": "update",
  "categories": [{"分类路径": "模块/功能", "分类说明": "范围", "关键词": "词一,词二"}],
  "cases": [{"用例编号": "TC-001", "用例标题": "检查项", "所属分类": "模块/功能", "测试步骤": "1. 执行操作", "预期结果": "1. 观察结果", "来源位置": "Sheet!A5:F5", "扩展字段": {"执行记录": null}}],
  "agent_notes": ["统计行未作为用例"]
}
```

计划内编号唯一，所属分类必须在计划或现有目录；未知用例键报错，请放入扩展字段。文本字段传字符串（或 null）；测试步骤、预期结果、需求编号、设计方法另接受字符串数组，扩展字段传可序列化 JSON 对象。版本允许缺失/null/空字符串。默认状态有效、审核待审核；计划可给已废弃。审核状态是元数据，不参与内容哈希。

按编号比对业务哈希：新增、未变、update/skip/conflict。业务哈希包含所有标准业务字段（缺值规范为空、状态默认有效、扩展字段规范JSON）；排除编号、来源定位、正文链接、审核状态、批次、哈希、时间。来源变化额外提示。`fail` 遇冲突停止全部写入，库内重复编号也冲突。`skip` 保留现有内容，正文不得写入被跳过的新内容。

原件同 SHA-256 已有导入批次链接时复用。正文包含分类全部有效用例；分类迁移时旧分类正文和计数也更新。废弃用例仍保留在 Base，退出有效正文与计数。

`targets.base=false, doc=true` 仅生成文档视图，不创建/更新用例记录；目录用例数仍来自实际 Base，有新增未入表的正文内容应在报告中明确解释。日常入库优先同时为 true。全 false 无效。

每次先 dry-run，核对数量和冲突，再用另一报告路径执行。原件上传后先登记部分完成批次，异常也保留原件身份；结束回读后更新批次结果。内容未变且链接和计数完整时不重写正文，变更时沿用原文档链接。正文按完整Markdown块分段，写结果未知先回读，确认前不重发append或create。报告含每条操作、步骤、链接、批次、回读完整性及原始错误。中断后先读回现状，不自动重试未知写入。跨会话重跑前 Agent 需核对已有原件、正文和分类资源。批次中的未确认正文创建会阻止盲目重建；目录已有同标题受管文档时复用最新修改的一份，报告列出候选与被替代的历史副本，不自动删除。


## 解除未确认正文创建的阻断

`document_unknown` 报告的 `next_steps` 给出原件 SHA-256、正文精确标题及本节入口。创建请求结果未知时保留阻断。若远端已出现同标题正文，重跑会先读目录并复用该文档，无需修改批次标记。

若正文始终不存在，Agent 按以下步骤处理：

1. 用 `maintain.py export` 导出该库备份并确认 `complete=true`；保存原始批次「说明」JSON。读取配置中的 `folders.bodies`，通过 `lark_io.list_folder(folder_token)` 完整分页读取正文目录；异常或权限不足时停止。核对精确标题、文档类型、受管目录及回收站/移动记录，等待异步创建稳定后再次完整读取。没有读到不能直接视为创建失败；无法排除权限、延迟或移动时保持阻断。
2. 将原件 SHA-256、标题、两次目录读回、相关权限与创建失败依据交给用户，取得“确认该正文未创建，允许重新创建”的明确答复。解除会允许下一次导入发起一次新的创建；原请求若后来成功可能产生重复文档，因此不能仅凭超时解除。
3. 用 `lark_io.list_records(base_token, tables['batches'])` 读取全部批次，要求 `complete=true`。找到**所有**「原件SHA256」匹配该 SHA 的批次，解析各行「说明」JSON；仅对 `body_attempts` 中 `title` 精确匹配、`confirmed` 不为 true、`failed_known` 不为 true 的条目增加 `failed_known: true`，保留 `confirmed: false` 和其余字段，并增加 `resolution` 对象记录确认人、时间和证据路径。示例：`{"title":"示例用例库 模块/功能","confirmed":false,"failed_known":true,"resolution":{"confirmed_missing":true,"evidence":"已确认的目录读回记录"}}`。不得删除整个说明、只处理最新批次或改变其他标题。修改前重新读取核对原始值，遇到并发变化停止。
4. 用 `lark_io.batch_update(base_token, tables['batches'], [{"record_id": "匹配批次的记录ID", "fields": {"说明": json.dumps(保留其他字段的说明对象, ensure_ascii=False)}}])` 写入这些精确行；只更新「说明」，保存请求和响应。必须 `status=ok`，再完整读回所有相关批次，确认标记和其余字段一致；结果未知时只读回、不重发。
5. 使用原计划先 dry-run，再以新报告路径执行导入。下一次仍先读正文目录；找到文档则复用，未找到才创建。核对报告、正文数、分类和用例链接，随后重复导入验证没有新增正文。任一步不完整时保留 partial，不重复创建。

上述操作由 Agent 使用已配置的飞书交互方法执行，不更改来源文件或公共模块。历史解除标记和证据保留在批次中；新导入批次另行记录新的创建结果。


## 字符串数组的机械规范化

为便于参考 Write 的同名字段，`测试步骤`、`预期结果`、`需求编号`、`设计方法` 可分别传字符串或字符串数组；不要求依赖 Write 的私有契约。每个数组元素必须为字符串，数字、null、对象及嵌套数组元素均拒绝。其他文本字段仍只接受字符串或 null。

- 步骤/预期：`["执行操作", "观察状态"]` 转为 `"1. 执行操作\n2. 观察状态"`，逐项从 1 编号，保留顺序和元素原文（含换行及已有编号，不猜测或删除）。
- 需求编号/设计方法：`["REQ-1", "REQ-2"]` 转为 `"REQ-1、REQ-2"`，不排序、不去重。
- 空数组转为空字符串；步骤和预期至少提供一个的原有规则保持。字符串、null 和缺失值沿用原有行为。

校验通过后，dry-run、Base 写入、正文与内容哈希使用同一规范化文本，不修改输入计划。数组与对应的文本形式哈希一致，切换表示形式不会触发更新；改变顺序或原文仍会触发内容变化。扩展字段内的数组保持原样。
