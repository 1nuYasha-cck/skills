# dev-flow 开发全流程 Skill

一个给 Claude Code / Codex 使用的开发流程 skill，用一份 `任务状态.md` 把一次需求从方案到提交串成六个阶段：

```text
项目初始化 → 技术方案 → 开发任务包 → 开发执行 → 代码评审 → 提交
```

每次运行时，agent 先检测项目是否已初始化、扫描未完成任务，再读取任务目录下的 `任务状态.md` 判断当前阶段，只执行这一个阶段，完成后写回状态。你只需要说「继续任务」或「完成下一步动作」，不用记住流程走到了哪一步。

## 功能

- **状态驱动**：阶段、阶段状态、下一步、评审轮次、待确认事项都记录在 `AGENT_WorkSpace/<任务>/任务状态.md`，不同 agent、不同会话之间靠它衔接。
- **六个阶段，各有产物**：

  | 阶段 | 主要产物 |
  | --- | --- |
  | 1 项目初始化 | `AGENT_WorkSpace/开发须知.md`；项目没有 `AGENTS.md` 时生成一份 |
  | 2 技术方案 | `<任务目录>/技术方案.md`、`任务状态.md` |
  | 3 任务包 | `开发任务包/1-任务声明.md`、`2-技术方案小节片段.md` |
  | 4 开发执行 | 代码修改、`开发任务包/实施与静态检查记录.md` |
  | 5 代码评审 | `<任务目录>/评审报告.md` |
  | 6 提交 | 代码在 git 仓库时提交（有上游则推送）；否则只登记基线 |

- **人工门禁**：技术方案确认、提交确认在任何模式下都必须由用户确认；任务包定位和开发执行前的回显在 agent 自检无问题时自动通过并记录；方案矛盾、开发前审查发现的问题、评审有条件通过的剩余条件，可以由你或派发 dev-flow 的调用方（其他 agent 或调度 skill）确认；路径、项目根、任务或差异基线不唯一时停止询问，不猜测。
- **诚实的验证边界**：区分静态检查与真实构建、运行、集成或目标环境验证，不把「编译通过」写成「验证通过」。
- **评审—修复循环**：评审不通过时默认停下，等你确认后进入开发执行（修复模式）；提需求时说明「评审不通过直接修复」则自动进入修复。累计评审 3 轮及以上仍不通过时，无论是否直接修复都会停下，由你决定继续修复、调整方案或停止。每轮修复追加到同一份实施记录。
- **规则与状态分离**：`AGENTS.md` 只放稳定规则，`开发须知.md` 放当前实现、进度和重要改动索引，避免用当前实现反向改写规则。
- **不含项目信息**：skill 只规定流程和硬约束。项目路径、代码位置、检查命令、提交约定都从你项目的 `AGENTS.md` 读取，换项目、换机器、换人都不用改 skill。
- **git 可选**：代码根是 git 仓库时评审基于 git diff、提交阶段提交代码；不是 git 仓库时用任务目录下的基线快照做评审，只登记不提交。
- **单 agent / 多 agent**：同一个 agent 逐步推进，或多个 agent 通过 `任务状态.md` 接力。
- **不内置调度**：dev-flow 只负责标准开发流程，不关心由谁、用什么工具推进下一阶段。需要用 herdr、Orca 等工具自动派发时，由对应工具的 skill 负责：发送一句「使用 $dev-flow 完成下一步动作：<阶段>（任务：<任务目录名>）」，执行者完成一个阶段并写好 `任务状态.md` 后结束，调用方以 `任务状态.md` 判断结果。

## 安装

见[仓库首页](../README.md#安装)。安装的是 `skills/dev-flow/` 目录，仓库根的文档和许可证不需要安装。

## 依赖

- Git（可选）：代码根是 git 仓库时用于评审差异和提交；推送需要已配置的上游和凭据。

## 在项目 AGENTS.md 中声明项目信息

dev-flow 需要的项目信息都可选，按正文读取，不要求固定格式。没写的使用缺省值：

| 信息 | 缺省 |
| --- | --- |
| 代码根（代码不在项目根时写明） | 项目根 |
| 需求 / 资料位置 | 在项目根内盘点 |
| 开发前同步要求 | git：fetch 后只做安全快进 |
| 静态检查 / 构建命令 | 按工具链自动选择常见检查 |
| 必须在目标环境做的验证 | 记为「未执行」 |
| 提交说明格式、语言 | 内置中文格式 |

需要精确命令时，在 AGENTS.md 中加一个 `## dev-flow` 小节（示例）：

```markdown
## 代码位置

代码根：`../my-service`（独立 git 仓库）

## dev-flow

### preflight
- `docker compose ps` 确认本地依赖服务已启动

### static_check
- 类型检查: `npm run typecheck`  (pass_when: exit==0)
- 单元测试: `npm test -- --run`  (pass_when: exit==0)
```

## 使用

在项目根目录下对 agent 说：

| 你说 | agent 做什么 |
| --- | --- |
| 「用 dev-flow 初始化这个项目」 | 生成 `AGENT_WorkSpace/开发须知.md`；没有 `AGENTS.md` 时根据项目内容生成一份并告诉你 |
| 「需求：……，请出技术方案」 | 新建任务目录，写技术方案，停下来等你确认 |
| 「方案确认」 | 记录确认，进入任务包阶段 |
| 「完成下一步动作」「继续任务」 | 读取状态，执行当前阶段 |
| 「修复评审问题」 | 确认评审不通过后的修复，按评审报告进入修复模式 |
| 「确认提交」 | 核对评审文件哈希，只暂存已评审文件并提交；有上游时推送 |

Codex 中也可以用 `$dev-flow` 显式调用，例如「使用 $dev-flow 完成下一步动作」。由其他 agent 或调度工具派发时，使用标准提示词「使用 $dev-flow 完成下一步动作：<阶段>（任务：<任务目录名>）」。

一个项目初始化后的目录大致如下：

```text
<项目根>/
├── AGENTS.md                      # 项目信息与规则（你维护）
└── AGENT_WorkSpace/
    ├── 开发须知.md
    └── <任务名称>/
        ├── 任务状态.md
        ├── 技术方案.md
        ├── 评审报告.md
        ├── 基线快照/                 # 仅非 git 代码
        └── 开发任务包/
            ├── 1-任务声明.md
            ├── 2-技术方案小节片段.md
            └── 实施与静态检查记录.md
```

## 目录结构

| 路径 | 内容 |
| --- | --- |
| `skills/dev-flow/SKILL.md` | 目录约定、项目信息来源、协作方式、运行流程、全局硬约束 |
| `skills/dev-flow/references/stage-*.md` | 六个阶段的工作流、边界和停止条件（每阶段一个文件） |
| `skills/dev-flow/references/state-file.md` | `任务状态.md` 的字段、状态迁移、确认门禁和一致性规则 |
| `skills/dev-flow/assets/` | 各阶段文档模板 |
| `skills/dev-flow/agents/openai.yaml` | Codex 界面显示信息 |
